# Proposed UrBackup upstream change: generic Linux block-device MBR fallback

## Status

This proposal was generated by OpenAI ChatGPT for the `urbackup-proxmox-agent`
project and has **not** been reviewed by a human software developer.

It is intended for review and testing before submission to UrBackup upstream.

## Problem

UrBackup's Linux image-backup path accepts a full `disk_path` and
`mapLinuxDev()` correctly leaves a valid block-device path unchanged.

However, `ClientConnector::sendMBR()` then calls
`parseDevicePartNumber()`. That parser recognizes only a fixed set of Linux
device-name families such as `sd`, `vd`, `loop`, `nvme`, and `nbd`.

Proxmox ZFS ZVOLs are exposed via paths such as:

```text
/dev/zvol/rpool/data/vm-150-disk-1
```

which resolve to Linux ZFS block devices such as:

```text
/dev/zd624
```

Neither naming form is handled by `parseDevicePartNumber()`. The MBR request
therefore fails before UrBackup reaches the external snapshot hook.

The validated temporary workaround used a symlink named `/dev/loop624`, but
that is not suitable as a production design and does not scale across VMs.

## Proposed behavior

If `parseDevicePartNumber()` cannot derive UrBackup's synthetic device and
partition numbers, `sendMBR()` should still attempt to read the already
resolved Linux block-device path directly.

The numeric fields can be set to `-1` when they cannot be derived.

This is intentionally more general than adding a hard-coded `zd` prefix. It
also supports other legitimate Linux block-device naming schemes that
UrBackup's parser does not currently know.

## Validated motivating case

Environment:

- Proxmox VE 9.2
- ZFS-backed QEMU VM disk
- UrBackup Server 2.5.37
- UrBackup Client 2.5.31

Observed failing request:

```text
MBR driveletter=_dev_zvol_rpool_data_vm-150-disk-1&disk_path=%2Fdev%2Fzvol%2Frpool%2Fdata%2Fvm-150-disk-1
```

Observed client failure:

```text
Error opening Device . No such file or directory
```

Using a temporary `/dev/loop624` alias proved that the remaining image path,
snapshot hook, full image backup, incremental image backup, and cleanup all
work successfully.

## Upstream submission plan

Before proposing this upstream:

1. build an UrBackup Linux client with the patch,
2. configure `image_letters` back to the native `/dev/zvol/...` path,
3. validate MBR retrieval without the loop alias,
4. validate `FULLI`,
5. validate `INCRI`,
6. verify snapshot and metadata cleanup,
7. then open an upstream issue/PR with the minimal reproducible case and test
   results.
